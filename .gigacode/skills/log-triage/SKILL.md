# log-triage — разбор логов

Цель: из тысяч строк получить 5–10 причин, понятных за минуту, и при необходимости
черновик дефекта. Повторы важнее потока: `NullPointerException ×847` — один дефект.

## 1. Источник логов (по порядку)

0. **`logs_analyze(service, minutes)`** — если в SimpleTest настроен источник логов (веб-коннектор):
   одна команда, ошибки уже сгруппированы. Список сервисов — `logs_saved_services`.
1. **MCP `simpletest`, прямой web-коннектор к dropup** — если источника нет:
   - `dropup_status` → если сессии нет, `dropup_login` (окно входа, входит человек; агент
     данные входа не вводит);
   - `dropup_projects` → уточнить у пользователя проект (стенд), если не назван;
   - `dropup_triage(namespace, service, since_minutes)` — группы ошибок уже посчитаны
     (шаг 2 ниже делать не нужно, только проверить и дополнить выводами);
   - `dropup_check(namespace)` — если вопрос «что со стендом» без конкретного сервиса;
   - `dropup_logs(..., grep=…)` — когда нужны сырые строки вокруг ошибки.
2. **Файл от пользователя** (.log, .txt, выгрузка) — группировать по шагу 2 самому.

Не использовать: `web-fetch` (у него нет SSO-сессии), API SimpleTest `/api/logs/*`
(в корп. контуре ни к чему не подключён), клики по консоли через `playwright` — для
этого есть готовые инструменты.

## 2. Группировка (для файла; dropup_triage делает это сам)

- Брать строки уровня ERROR/FATAL, стектрейсы целиком, HTTP 5xx.
- Отпечаток (fingerprint) = текст ошибки, где числа, UUID, hex, IP, время и id
  заменены на `<n>`, `<uuid>`, `<hex>`, `<ip>`, `<ts>`; для стектрейса — исключение +
  первые 3 кадра своего кода.
- По каждой группе: количество, первое и последнее появление, поды.

Категории: NPE · timeout · config · auth · db · network · memory · serialization · other.
Важность: **critical** — сервис не отвечает или падает (CrashLoop, OOM); **high** —
ошибка в основном сценарии, массово; **medium** — есть обход или единичные; **low** —
шум, предупреждения.

## 3. Отчёт

```
TL;DR: 1–2 предложения — что сломано и насколько массово.

| # | Ошибка (отпечаток) | Кол-во | Первая / последняя | Поды | Категория | Важность |

Топ-риски: 1–3 пункта.
Вопросы: что нужно уточнить у пользователя (стенд, версия, сценарий).
```

## 4. Черновик дефекта

Через `simpletest_format_bug` (шаблон SimpleTest, коротко и по сути) — передать суть
ошибки, сервис и ключевую строку лога. Без MCP — тот же формат вручную:

```
# [Back][Модуль] Краткая суть

## Описание
1–2 предложения: что сломано и где.

## Шаги воспроизведения
1. ...

## Фактический результат
Что происходит + ключевая строка ошибки в code-блоке (не весь лог).

## Ожидаемый результат
Как должно быть.

Приоритет: Высокий
```

Без разделов «Окружение» и «Гипотезы».

## 5. Создание в Jira

Только после явного «создавай» от пользователя. Через MCP `jira`, проект SBER911;
формат полей (КЭ, ИТ-услуга, среда, тип стенда) — строго по `backend/api/jira_constants.py`.
После создания — вернуть ключ и ссылку на дефект.
