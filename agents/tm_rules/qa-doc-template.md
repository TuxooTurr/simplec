# Структура документа QA

Та же структура, что у документа QA в разделе «Данные» в Shark. Включай только те разделы, для которых есть информация в требованиях.

## Что это такое простыми словами

Что делает фича. Зачем она нужна и какую проблему решает. Кто ею пользуется (роли). Откуда берутся данные и куда уходят. Новый человек в команде должен понять это за две минуты.

## Модель данных

Для каждой таблицы или сущности: таблица полей (поле, тип, обязательность, описание) и связи. ER-диаграмма в PlantUML (`entity`, связи `||--o{`).

## Диаграммы

Для каждого значимого процесса диаграмма PlantUML:

- Activity — алгоритмы и ветвления;
- Sequence — взаимодействие компонентов, не смешивать `package` и `participant`;
- Component — архитектурные схемы, использовать `component`, а не `participant`.

Начинать с `@startuml`, заканчивать `@enduml`. Идентификаторы только латиницей, для кириллицы алиасы: `participant "Имя" as Name`.

## Условия и бизнес-логика

Таблица: условие → результат. Важные правила и ограничения.

## API методы

Сводная таблица методов. Для каждого: назначение, роли и доступ, параметры запроса (параметр, тип, обязательность, описание), параметры ответа (параметр, тип, описание, источник данных).

## Jobs и фоновые задачи

Для каждого Job: что делает, периодичность, алгоритм по шагам, какие таблицы читает и пишет.

## Интеграции и потоки данных

Для каждого потока: источник → канал → приёмник, формат данных (топики Kafka, REST, файлы), параметры подключения.

## Сервисы и КЭ

Таблица: сервис | роль в фиче | КЭ. КЭ только из `_tech/ke-services.md`, сервиса нет в таблице — `⚠`.

## Чек-лист проверок

Плоский список, не больше 40 пунктов. Каждый пункт — утверждение, проверяемое как истина или ложь: «АС из списка исключений получают value=NULL», а не «проверить, что…». Покрывай ключевые функции, граничные случаи, негативные сценарии, формулы, статусы и условия доступа.

## Вопросы для уточнения

Таблица: № | Вопрос | Приоритет (блокирует / неясность / мелочь). Только реальные противоречия, неясности и пропуски.

---

Правила:

- Не придумывай информацию, которой нет в требованиях.
- Не пиши «предположительно»: неясное переноси в вопросы.
- Не дублируй одно и то же в разных разделах.
- Секреты и реальные персональные данные в документ не включай.
