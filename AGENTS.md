# Shark — единая инструкция для любого ИИ-агента

Актуализировано: 21.11.2026. Этот файл используется независимо от модели, редактора и способа запуска агента. Если среда не читает `AGENTS.md` автоматически, приложите его к запросу или явно попросите прочитать. Отдельные инструкции для Claude, Codex и ГигаКод не ведутся.

## Порядок работы

- Текущий запрос пользователя определяет задачу и имеет приоритет над сохранённым контекстом.
- Перед изменением изучите актуальный код и состояние Git. Сохраняйте чужие и ранее сделанные изменения; не сбрасывайте рабочее дерево.
- Доводите разрешённую работу до проверяемого результата. Рутинные обратимые действия не требуют повторного согласования.
- Не создавайте новую архитектуру, зависимости или копии общих компонентов без необходимости.
- Коммит, push, публикацию и действия во внешних системах выполняйте в пределах запроса пользователя. Черновик дефекта показывайте до создания; явная команда создать или отправить уже является разрешением.
- Секреты, содержимое переписки и корпоративные логи не выводите в чат, заметки и отчёты.
- Мок-проверка подтверждает локальный сценарий. Работу корпоративной интеграции подтверждает только проверка на реальном источнике.

## Совместимость и сохранность данных

Прежние названия — SimpleTest и Loom. Переименование Shark визуальное. Без отдельной миграции сохраняйте:

- `simpletest.db`, параметры и имена существующих PostgreSQL-баз, пользователей и томов;
- формат `simpletest.backup`, метку `__SIMPLETEST_REDACTED__`;
- свойства Confluence `simpletest-stand`, `simpletest-probe`, `simpletest.stand-schedule`, `source: "simpletest"`;
- связи Jira `simpletest:zephyr-run:…`, `simpletest.zephyr`;
- каталог `~/.simpletest/`, переменные `SIMPLETEST_SECRET_KEY`, `SIMPLETEST_SECRET_KEY_FILE`, `SIMPLETEST_URL`, `SIMPLETEST_LOGIN`, `SIMPLETEST_PASSWORD`;
- каталог `/opt/simpletest`, существующий домен и службы `simpletest-api`, `simpletest-next`, `simpletest-runners`;
- действующие `st_*` ключи localStorage/sessionStorage и сохранённые пользовательские данные.

Пути JSON-хранилищ берите из `db.paths.DATA_DIR`; не создавайте собственный жёстко заданный путь `data/`. Учитывайте `SHARK_DATA_DIR` и `SHARK_MOCK`. Перед переустановкой сохраняйте данные и ключ шифрования по [инструкции переноса](MIGRATION.md).

`agents/tm_rules/rules.md`, `ke-services.md` и `qa-doc-template.md` в той же папке — рабочие входы генератора. Не удаляйте их как документацию. Структура фич для генерации берётся из дерева «Данных». Нельзя подменять её устаревшим статическим списком.

## Конфигурация и подключения

- Основные подключения редактируются в `/settings`. Корпоративные дополнения подключаются через внешний `SHARK_ENV_FILE`; пример — `config/corporate.env.example`.
- `.env` и `frontend/.env.local` исторически отслеживаются Git. Игнорирование не прекращает отслеживание. Не перезаписывайте их шаблонами и не добавляйте новые секреты; используйте окружение, внешние файлы и предусмотренные UI-хранилища.
- Ключ шифрования нужен для чтения сохранённых техучёток. Не меняйте его попутно и не включайте в обычную резервную копию.
- GigaChat имеет встроенные профили Личный, Corp и IFT (`GIGA_PROFILES`). Сторонние chat/completions-compatible провайдеры добавляются в UI. Выбранную модель берите из `WorkspaceContext` и передавайте явно.
- Вход — через Jira либо локальную универсальную учётку из `backend/api/auth.py`. Bearer-сессии находятся в памяти. Ограничение редактирования Главной отдельно задаётся `DASHBOARD_EDITORS`.
- Для TLS используйте корпоративную цепочку CA и необходимые клиентские сертификаты; [инструкция CA](certs/README.md). Не отключайте проверку TLS по умолчанию.
- PVS и Эфир подключайте по [PVS](docs/pvs-mcp.md) и [Эфиру](docs/efir-mcp.md). Сверяйте фактический `tools/list`, версию пакета и формы ответов внутри контура. Не выдумывайте инструменты и права доступа.
- Legacy MCP в `mcp_server/` и `scripts/loom-mcp.sh` сохранён для явно запрошенных сценариев dropup. Список инструментов проверяйте в коде и `tools/list`. Один процесс на профиль браузера; для нескольких клиентов предусмотрен `scripts/loom-mcp.sh --http` на `127.0.0.1:8765/mcp`. Веб-операция `web_run` может изменять внешнюю систему и требует соответствующего разрешения пользователя.

## Правила реализации

- Новый API: модуль в `backend/api/` → роутер в `backend/main.py` → клиент в `frontend/lib/` → интерфейс раздела. Клиенты используют `authHeaders()`.
- Поля Jira берите из `jira_constants.py` и актуальных `createmeta/editmeta` выбранного проекта и типа. Не отправляйте поля, отсутствующие на доступном экране.
- Отображаемое имя Shark не меняет сохранённые форматы и связи.
- Длинные операции выполняйте фоном с прогрессом и возможностью отменить оставшуюся работу. Закрытие формы не должно приводить к потере результата. Разделяйте таймаут одного внешнего вызова и всей операции.
- Ошибка обновления не должна заменять последние известные данные пустым списком или нулём. Неполную выборку обозначайте.
- Общая отметка «Обработано» относится к очереди виджета и не меняет статус Jira. Изменение статуса Jira после обнаружения задачи автоматически проставляет эту отметку; учитывайте доступную историю переходов и отмену обработки. Опрос не гарантирует обнаружения кратковременного совпадения JQL или перехода с возвратом при недоступной истории; строгая гарантия требует отдельно согласованного источника событий Jira.
- На Главной два типа виджетов: список с представлениями таблица/кольцо/гистограмма и самостоятельный счётчик. Счётчик — только название и огромная цифра; ноль зелёный, размер всегда маленький квадрат S без растягивания. По последнему рисунку владельца размеры S/M/L/XL/XXL фиксированы в пикселях; S не увеличивается с шириной монитора, XXL занимает всю ширину. Размеры и миграция описаны в [инструкции Главной](docs/dashboard.md). Панель Эфира с Главной убрана (решение владельца 23.11.2026), код сохранён. Размер виджета растёт только до соседей, сетка центрирована.
- График объединяет списки Jira tool: папка — строка команды, передача на ИФТ/ПСИ — начало, плановое окончание Jira — конец. ИФТ → Major-Check, ПСИ → Major-GO; отдельный ПРОМ не добавляется.
- Новые скрипты алертов могут передавать ответ чату маркером `@@ST_MSG ` + JSON с `topic`, `body`, `recipients`, `key`; парсер — `frontend/lib/kernelMessages.ts`. Существующие секреты скриптов не копируйте в новые места.

## Интерфейс

- Используйте существующие `frontend/components/ui/`, CSS-переменные `frontend/app/globals.css` и Tailwind-токены. Сохраняйте светлую/тёмную темы.
- Отступы рабочей зоны — как в Jira tool: `p-6`, шапка `px-6 py-3`; без случайного центрирования.
- Результат размещается сбоку при одной рабочей зоне и снизу при двух (`useSplitView()`). «Данные» используют всю рабочую область.
- Используйте общий `Select`, общий `Modal` и его `footer`. У именованных окон сохраняйте сворачивание на полку и индикацию фоновой работы.
- Формы, которые должны пережить переход между разделами, открывайте через `openForm` / `FormHost` из `frontend/lib/backgroundForms.ts`. Обработчики завершения должны работать и после размонтирования раздела.
- Для одиночных и массовых действий используйте общие таблицы и формы задач. Не создавайте альтернативные формы без необходимости.
- Уведомления отправляйте через `notify()` из `frontend/lib/notifications.ts`; для результата в открытом разделе предусмотрен `silent: onPage(...)`.
- Общие действия шапки находятся в `frontend/components/TopActions.tsx`. Сохраняйте единый порядок и оформление.

## Проверки и сопровождение

Запускайте проверки, соответствующие изменению, из окружения проекта:

```bash
python -m pytest tests -q
npm run typecheck --prefix frontend
npm run build --prefix frontend
```

Для изменения только документов достаточно проверить ссылки, команды и сохранность рабочих Markdown-промптов. Полный прогон нужен при изменении поведения. В отчёте различайте тесты, моки и корпоративные проверки; указывайте ограничения.

При изменении поведения обновляйте существующий профильный документ. Не возвращайте отдельные инструкции для разных моделей и не дублируйте описание кода огромными деревьями файлов. История изменений — Git; пользовательские изменения — `frontend/lib/releaseNotes.ts`.

При порученном push в `main` обновите «Что нового». Версия соответствует дню push: `<год − 2024>.<месяц тремя цифрами>.<день>` (21.11.2026 → `2.011.21`). Все записи одного дня имеют одну версию; у новой записи уникальный `id`. Дата коммита не заменяет дату push.
