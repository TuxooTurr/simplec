# Перенос данных и серверное развёртывание Shark

Актуализировано: 21.11.2026. Первичная локальная установка описана в [README](README.md), корпоративная настройка и приёмка — в [инструкции запуска](docs/gigacode-launch.md).

## Перед переносом или обновлением

1. В Shark выгрузите все разделы через «Резервная копия», включая браузерные данные Jira tool. Часть состояния списков хранится в браузере: копирования серверного каталога недостаточно.
2. Сохраните конфигурацию, расположение данных и способ передачи ключа шифрования. Не публикуйте секреты и не перезаписывайте действующую `.env` шаблоном.
3. Для точного переноса файлов остановите запись в старый экземпляр. SQLite переносите при остановленном приложении либо штатным SQLite backup; PostgreSQL — средствами резервного копирования PostgreSQL.
4. Скопируйте данные с сохранением структуры каталогов, владельцев и прав. Выполняйте перенос по защищённому каналу.

Штатная JSON-копия скрывает секреты; сертификаты, ключи и JDBC JAR в неё не входят. Она не заменяет полный перенос хранилищ. При загрузке выберите режим: **«Дополнить»** (по умолчанию) сохраняет существующие значения и добавляет недостающие записи, **«Перезаписать»** заменяет представленные в копии файлы/таблицы и значения настроек. Невыбранные разделы и хранилища, которых нет в копии, сохраняются. Это относится и к данным браузера. Перед изменением создаётся серверный снимок в `SHARK_DATA_DIR/backups/` (обычно `data/backups/`), сохраняются последние пять. Секреты берутся из текущей установки по идентификатору записи; на новом хосте их вводят заново. Подробное поведение — `backend/api/backup.py`.

Раздел **«Главная»** включает настройки списков и счётчиков: JQL, период, колонки, источник ST, диаграмму, палитру, цвета групп, размеры, позиции и общую очередь с историей обработки. В копию входят также ширины таблиц и личные настройки панели Эфира из браузера. При дополнении существующие настройки виджета и отметки обработки сохраняются, новые виджеты размещаются без наложения. Повторная загрузка одной копии не создаёт дубли записей с теми же идентификаторами. Значения ST находятся в Jira tool: для их переноса выберите также **«Jira tool»** либо **«Все разделы»**. После восстановления перезагрузите страницу; при успешной записи приложение делает это автоматически.

## Что переносится отдельно

| Данные | Расположение и действие |
|---|---|
| JSON-хранилища и вложения | Весь активный `SHARK_DATA_DIR` либо `data/`, включая `dashboard.json`, требования, справочники, настройки и `requirement_assets/` |
| Основная БД | Файл по фактическому SQLite `DATABASE_URL` либо дамп PostgreSQL. Не предполагайте, что любая установка использует `simpletest.db` |
| RAG | Существующие `db/chroma_db/`, `db/chroma_data/`; проверьте используемый путь в `db/vector_store.py` |
| JDBC | Реестр `jdbc_drivers.json` и каталог `jdbc_drivers/` внутри каталога данных; внешние JAR переносите отдельно |
| Ключ шифрования | Сохраните используемый источник `SIMPLETEST_SECRET_KEY` / `SIMPLETEST_SECRET_KEY_FILE` и локальные ключи хранилищ сертификатов. Передавайте отдельно от обычной копии |
| Сертификаты | Корпоративный CA, клиентские cert/key, локальные хранилища сертификатов и `certs/ca-bundle.pem`, если используется |
| Конфигурация | Действующие `.env`, `frontend/.env.local`, внешний `SHARK_ENV_FILE`, секреты окружения и параметры служб |
| MCP | Утверждённая сборка PVS, её окружение, команда запуска и доступы. Пароль берётся из разрешённого источника внутри контура |
| Эфир | На новом хосте предпочтительно выполнить SSO заново. Зашифрованная Cookie требует прежнего ключа; браузерный профиль не заменяет проверку доступа |
| Автотесты | Внешняя папка фреймворка и её параметры, если используется сохранённый код запуска автотестов |

Не удаляйте «неизвестные» JSON и ключи при переносе. Если путь в настройках абсолютный, укажите новый через UI: сертификаты LLM/Kafka/PVS, внешние JAR, браузер, каталог фреймворка.

## На новой машине

1. Установите зависимости по README; восстановите нужные данные до запуска.
2. Проверьте права ОС на каталог данных и ключи. При смене владельца исправьте доступ без расширения прав на секреты.
3. Настройте действительный `DATABASE_URL` и внешний корпоративный файл. Для корпоративных дополнений используйте `SHARK_ENV_FILE`.
4. Запустите **один** API worker и frontend.
5. При переносе через UI импортируйте только нужные разделы резервной копии. Заново задайте скрытые секреты, затем проверьте результат.

## Развёртывание сервера

`deploy.sh` — сохранённый сценарий для Ubuntu/Debian/AlmaLinux с доступом к системным пакетам, Node.js, Python, Java, nginx и certbot. Перед запуском изучите скрипт и задайте целевые `DOMAIN`, каталог и параметры установки. Он изменяет систему, настраивает службы и может выпускать публичный сертификат. Для закрытого контура используйте утверждённые зеркала и сертификаты; не запускайте сценарий публичного VPS как универсальную корпоративную установку.

Существующие имена служб и каталогов сохраняются для совместимости:

| Служба | Запуск |
|---|---|
| `simpletest-api` | `python -m uvicorn backend.main:app`, локальный порт 8000, один worker |
| `simpletest-next` | `node frontend/.next/standalone/server.js`, локальный порт 3000 |

nginx направляет `/` на frontend, `/api`, `/healthz`, `/docs` и `/openapi.json` на API. Для WebSocket требуется Upgrade. Для автоматических опросов и публикаций backend должен постоянно работать.

При обновлении сначала сохраните данные и проверьте рабочее дерево. Получите согласованную версию кода, установите изменившиеся Python-зависимости из окружения службы и зависимости frontend по lock-файлу. Пересоберите frontend:

```bash
npm ci --prefix frontend
npm run build --prefix frontend
```

Если служба запускает standalone, обновите статику и `public/` рядом с `server.js` до перезапуска. При копировании сохраняйте размещение, которое использует `deploy.sh`; не создавайте вложенные `static/static` при повторном обновлении.

```bash
sudo systemctl restart simpletest-api simpletest-next
sudo systemctl status simpletest-api simpletest-next
sudo journalctl -u simpletest-api -n 50
```

## Проверка результата

- `GET /healthz` отвечает успешно; после входа открывается «Главная».
- На месте списки и папки Jira tool, документы, расписание стендов и история очереди Главной. Общая отметка обработки видна двум пользователям.
- Подключения используют новые пути; сохранённые техучётки расшифровываются либо заданы заново.
- Выбранные LLM и JDBC работают, если нужны этой установке.
- В корпоративной сети выполнена [приёмка PVS, Эфира, Jira и Confluence](docs/gigacode-launch.md). Отдельно проверены фоновые обновления при закрытом браузере.
- Старую копию данных сохраняйте до подтверждения результата пользователем.
